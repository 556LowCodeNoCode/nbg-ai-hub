## 2. Η βασική διαπίστωση: πού πραγματικά βρίσκεται η πληροφορία

Η αρχική παραδοχή ήταν ότι «ο κύριος όγκος της πληροφορίας θα έρχεται από τα εισηγητικά».
Η αντιστοίχιση που φτιάξαμε δείχνει κάτι πιο σύνθετο:

| Πηγή | Πεδία σύμβασης | % |
|---|---|---|
| Εισηγητικό — άμεσα | 21 | 10% |
| Εισηγητικό — έμμεσα (χρειάζονται μετατροπή/σύνταξη) | 17 | 8% |
| **Δεν προκύπτουν από το εισηγητικό** | **170** | **82%** |

Αυτό **δεν** ακυρώνει την παραδοχή — την ακριβολογεί:

- Το εισηγητικό δίνει τα **αποφασιστικά** πεδία: αντικείμενο, ανάδοχος, τίμημα, διάρκεια,
  μοντέλο παροχής. Δηλαδή *τι* σύμβαση θα γίνει και με ποιους όρους εμπορικά.
- Τα 170 που «λείπουν» δεν λείπουν πραγματικά — είναι **νομικές παράμετροι** (ποινικές ρήτρες,
  εγγυητικές, όρια ευθύνης, προθεσμίες καταγγελίας, μηχανισμοί GDPR). Αυτά δεν τα αποφασίζει
  ο εισηγητής· είναι **πολιτική της Τράπεζας** και σήμερα ζουν μέσα στα κεφάλια της Νομικής
  και στα προηγούμενα έγγραφα.

**Συνέπεια για τον σχεδιασμό:** το δύσκολο κομμάτι δεν είναι η συναρμολόγηση του κειμένου —
είναι η **εφοδιαστική αλυσίδα των δεδομένων**. Χρειαζόμαστε μια **Βιβλιοθήκη Προτύπων Όρων**
με εγκεκριμένες προεπιλογές ανά τύπο σύμβασης. Χωρίς αυτήν, η αυτοματοποίηση σταματά στο 18%.

## 3. Αρχιτεκτονική: τέσσερα μητρώα και μία μηχανή

```
┌─ ΜΗΤΡΩΑ (δεδομένα) ──────────────────────────────────────────────┐
│                                                                   │
│  1. Μητρώο Πεδίων          τι πεδία υπάρχουν, τύποι, κανόνες      │
│     (DATA_MODEL × 2)        εισηγητικό ⇄ σύμβαση                  │
│                                                                   │
│  2. Μητρώο Άρθρων           κάθε άρθρο ως module: ζώνη, συνθήκη,  │
│     (module registry)       tokens, παραπομπές, ιδιοκτήτης, έκδοση│
│                                                                   │
│  3. Βιβλιοθήκη Προτύπων     εγκεκριμένες προεπιλογές για τις      │
│     Όρων  ← ΤΟ ΚΕΝΟ         170 νομικές παραμέτρους ανά τύπο      │
│                                                                   │
│  4. Μητρώο Κανόνων          R-xx (σύμβαση) + Ε-xx (εισηγητικό)    │
│     (rule registry)         σε ενιαία ταξινομία                   │
└───────────────────────────────────────────────────────────────────┘
                              ↓
┌─ ΜΗΧΑΝΗ (ροή) ────────────────────────────────────────────────────┐
│  Πρόσληψη → Έλεγχοι → Επιλογή προτύπου → Επίλυση πεδίων →         │
│  Συναρμολόγηση άρθρων → Παραγωγή → Πύλες ελέγχου → Αναθεώρηση     │
└───────────────────────────────────────────────────────────────────┘
```

Τα μητρώα 1 και 4 υπάρχουν ήδη σε μεγάλο βαθμό. Το 2 υπάρχει μερικώς (`module_map.json`).
Το 3 **δεν υπάρχει** και είναι η κρίσιμη προϋπόθεση.

## 4. Η ροή σε οκτώ στάδια

### Στάδιο 0 — Πρόσληψη δεδομένων εισηγητικού

Δύο δρόμοι, και η επιλογή καθορίζει το πόσο αξιόπιστο θα είναι όλο το σύστημα:

**(α) Δομημένη φόρμα εισηγητικού** — ο εισηγητής συμπληρώνει πεδία· από αυτά παράγεται
*και* το εισηγητικό *και* τροφοδοτείται η μηχανή συμβάσεων. Μία πηγή αλήθειας.

**(β) Εξαγωγή από το υπάρχον εισηγητικό** — το έγγραφο γράφεται όπως σήμερα και ένας
extractor βγάζει τα πεδία, με επιβεβαίωση από άνθρωπο.

Τα 3 δείγματα που εξετάσαμε έχουν **ριζικά διαφορετική δομή** μεταξύ τους: άλλες επικεφαλίδες
(«Α. Εισαγωγή – Περιγραφή προμήθειας» vs «Α. Περιγραφή προμήθειας»), άλλο σύστημα αναγνώρισης
(αρ. πρωτοκόλλου vs κωδικός στο υποσέλιδο vs τίποτα), πίνακες με εντελώς διαφορετικά σχήματα.
Η εξαγωγή θα είναι εύθραυστη. **Η (α) είναι στρατηγικά σωστή· η (β) είναι η ρεαλιστική
μετάβαση.** Πρόταση: (β) τώρα με υποχρεωτική επιβεβαίωση, (α) ως στόχος.

### Στάδιο 1 — Πύλες εισόδου (blocking)

| Κανόνας | Έλεγχος |
|---|---|
| Ε-02 | Εγκεκριμένη σκοπιμότητα; αλλιώς stop |
| Ε-10 | Θετική απόφαση εγκριτικού οργάνου; αλλιώς stop |
| Ε-17 | Υπάρχει μοναδικό κλειδί εισηγητικού; αλλιώς προειδοποίηση |

### Στάδιο 2 — Επιλογή προτύπου (Ε-01)

```
memo.procurement_type = Υπηρεσίες      ∧ ¬is_continuation  → Γ (IT CONSULTING)
memo.procurement_type = Πλατφόρμα      ∨ deployment = SaaS  → Β (IT SOLUTION)
memo.procurement_type = Σύστημα        ∨ deployment = on-prem → Α (IT PLATFORM)
is_continuation = Ναι ∨ type = Ανανέωση                      → Δ (ADDENDUM)
```

Προσοχή στο **Ε-06**: αν οι ανάδοχοι είναι >1 (όπως στο Ε2 με EY/Deloitte/Desquared),
παράγονται **τόσες συμβάσεις όσοι οι ανάδοχοι**, καθεμία με το δικό της ανώτατο ποσό —
όχι μία σύμβαση με το συνολικό.

### Στάδιο 3 — Επίλυση πεδίων με ιχνηλασιμότητα

Κάθε ένα από τα 208 πεδία επιλύεται με **σειρά προτεραιότητας πηγών**:

| # | Πηγή | Πλήθος | Παράδειγμα |
|---|---|---|---|
| P1 | Εισηγητικό | ~38 | `commercials.total_price` ← `recommendation.approved_amount` |
| P2 | Μητρώα (ΓΕΜΗ, προμηθευτών, συμβάσεων) | ~15 | `vendor.legal_name`, `vendor.vat_number`, `original_contract.number` |
| P3 | Προσφορά / Τεχνική Προσφορά | ~25 | τεχνικά χαρακτηριστικά, SLA, rate cards |
| P4 | **Βιβλιοθήκη Προτύπων Όρων** | ~110 | `penalties.cap_pct`, `liability.cap_pct`, `cure_period_days` |
| P5 | Ανθρώπινη είσοδος | ~20 | `project.work_location`, ελεύθερα κείμενα |

Κάθε πεδίο κουβαλά **provenance**: τιμή, πηγή, βαθμός βεβαιότητας, αν είναι προεπιλογή ή
παρέκκλιση. Η παρέκκλιση από P4 απαιτεί ρητή έγκριση του Επιχειρησιακού Χώρου Προμηθειών. Αυτό είναι απαραίτητο και για
τον εποπτικό έλεγχο: πρέπει να μπορεί να απαντηθεί «γιατί αυτή η σύμβαση λέει 5% και όχι 10%».

**Παράγωγα πεδία:** τα `.in_words` (ολογράφως) **δεν πληκτρολογούνται** — υπολογίζονται.
Το ίδιο τα `total_incl_vat`, τα αθροίσματα οροσήμων, οι ημερομηνίες λήξης από διάρκεια.
Στο μοντέλο υπάρχουν δεκάδες τέτοια· κάθε ένα που πληκτρολογείται είναι μια ευκαιρία για
ασυμφωνία αριθμητικών/ολογράφως — κλασική πηγή νομικών διαφωνιών.

### Στάδιο 4 — Συναρμολόγηση άρθρων

Εδώ μπαίνει το μοντέλο ζωνών (βλ. §5). Κάθε άρθρο είναι module με συνθήκη ένταξης.
Μετά την ένταξη/εξαίρεση, **η αρίθμηση ξαναϋπολογίζεται** και οι παραπομπές επιλύονται
**συμβολικά**.

Αυτό λύνει τρία τεκμηριωμένα προβλήματα ταυτόχρονα:
- τα σφάλματα αρίθμησης & παραπομπών (§5.2 της ανάλυσης)
- το «άρθρο xxx» του Παραρτήματος Μέτρων Ασφάλειας
- το «άρθρο ……» του Παραρτήματος Πίνακα Τιμών

### Στάδιο 5 — Παραγωγή εγγράφου

Αντικατάσταση tokens στο πρότυπο (.docx), συναρμολόγηση παραρτημάτων, παραγωγή πινάκων
(τιμών, οροσήμων, ρητρών) από δομημένα δεδομένα, εισαγωγή αρίθμησης.

### Στάδιο 6 — Πύλες εξόδου (validation)

| Έλεγχος | Τι πιάνει |
|---|---|
| Πληρότητα | κανένα `{{...}}`, `……`, `xxx` δεν έμεινε |
| Ε-13 | τίμημα ≤ εγκεκριμένο ποσό |
| Ε-14 | ημερομηνία υπογραφής ≥ ημερομηνία απόφασης |
| Ε-08 | ΦΠΑ συνεπές |
| Ε-11 / Ε-22 | αθροίσματα ανθρωποημερών & κόστους |
| Παραπομπές | κάθε «άρθρο Ν» δείχνει σε υπαρκτό άρθρο |
| **Μόλυνση** | καμία επωνυμία/ποσό από άλλη συμφωνία |

Ο τελευταίος αξίζει ιδιαίτερη μνεία: είναι το πρόβλημα §5.1 (πρότυπα «μολυσμένα» από
προηγούμενες συμφωνίες). Ένας αυτόματος έλεγχος «υπάρχει στο κείμενο όνομα προμηθευτή που
δεν είναι ο ανάδοχος αυτής της σύμβασης;» το πιάνει αμέσως — κάτι που ο ανθρώπινος έλεγχος
αποδεδειγμένα δεν έπιασε.

### Στάδιο 7 — Ανθρώπινη αναθεώρηση

Στον ελεγκτή δεν παρουσιάζεται «ένα νέο έγγραφο» αλλά **διαφορά ως προς το εγκεκριμένο πρότυπο**:
τι μπήκε, τι βγήκε, ποιες παράμετροι αποκλίνουν από τις προεπιλογές, ποια πεδία Ζώνης 4
γράφτηκαν από άνθρωπο. Ο χρόνος ελέγχου πέφτει από «διάβασε 40 σελίδες» σε «έλεγξε 12 σημεία».

## 5. Το μοντέλο των άρθρων: ζώνες και modules

Από την ανάλυση:

| Ζώνη | Ποσοστό κειμένου | Περιεχόμενο | Χειρισμός |
|---|---|---|---|
| **1 — Boilerplate** | ~85% | Εμπιστευτικότητα, GDPR, BRRD, δικαιώματα ΤτΕ, ανωτέρα βία | Κλειδωμένο, versioned από Νομική |
| **2 — Παραμετρικό** | ~10% | Μέρη, ποσά, ημερομηνίες, ορόσημα, ποσοστά | Auto-fill από τα μητρώα |
| **3 — Υπό όρους** | ~4% | Escrow, εγγυητική, υπεργολάβοι, SLA, εξοπλισμός, μεταβατική υποστήριξη | Κανόνες ένταξης |
| **4 — Ελεύθερο** | ~1% | Περιγραφή αντικειμένου, ειδικές διαπραγματευμένες ρήτρες | **Πάντα άνθρωπος** |

Κάθε module χρειάζεται εγγραφή με: `id`, τίτλος, ζώνη, σε ποια πρότυπα ισχύει (Α/Β/Γ/Δ),
**συνθήκη ένταξης** (έκφραση πάνω σε πεδία), tokens που καταναλώνει, παραπομπές προς/από,
ιδιοκτήτη (Νομική/Ασφάλεια/Προμήθειες) και έκδοση.

Το `module_map.json` που υπάρχει καλύπτει το χαρτογραφικό μέρος αλλά **δεν** φέρει ζώνη,
συνθήκη και ιδιοκτήτη. Αυτή η επέκταση είναι το δεύτερο μεγάλο κομμάτι δουλειάς μετά τη
Βιβλιοθήκη Όρων.

**Τα 4 παραρτήματα σε αυτό το μοντέλο** (όπως καταλήξαμε):
- GDPR → Ζώνη 1 + δύο λίστες τιμών (κατηγορίες δεδομένων/υποκειμένων)
- Μέτρα Ασφάλειας → Ζώνη 1 + πίνακας πιστοποιήσεων υπό όρους (5 σημαίες, οι 3 λείπουν από το μοντέλο)
- Πίνακας Τιμών → Ζώνη 2, συμπληρώνεται από λειτουργό / παράγεται από την προσφορά
- Διαδικασία Παραλαβής → Ζώνη 1 **με ενσωματωμένες παραμέτρους** που συγκρούονται με πεδία
  του μοντέλου (5/3/10 ημέρες, 3 μήνες εγγύηση). Χρειάζεται απόφαση: tokenize ή κλείδωμα.

## 7. Ρεαλιστικός βαθμός αυτοματοποίησης

Ας μην υποσχεθούμε «100% αυτόματα»:

| Μέτρηση | Εκτίμηση |
|---|---|
| Κείμενο που συναρμολογείται χωρίς άνθρωπο | ~99% (Ζώνες 1+2+3) |
| Πεδία που γεμίζουν αυτόματα **σήμερα** | ~18% (μόνο P1) |
| Πεδία που γεμίζουν αυτόματα **με Βιβλιοθήκη Όρων** | ~85% |
| Σημεία που απαιτούν ανθρώπινη κρίση ανά σύμβαση | ~12–20 |

Δηλαδή: **ο στόχος είναι «σχέδιο σύμβασης σε λεπτά αντί για ημέρες, με 15 σημεία προς έλεγχο»**,
όχι σύμβαση χωρίς δικηγόρο. Αυτό είναι και το ειλικρινές μήνυμα προς τη Διοίκηση.

## 8. Τι χρειάζεται το interactive HTML

Το `DECISION_RULES_interactive.html` σήμερα καλύπτει μόνο τους κανόνες συμβάσεων. Για να
γίνει το εργαλείο πλοήγησης όλου του μηχανισμού, χρειάζεται:

1. **Οι κανόνες Ε-01…Ε-22** των εισηγητικών, δίπλα στους R-xx
2. **Ταξινομία & σοβαρότητα** (R-T/R-A/R-F/R-V, blocking/warning) με φίλτρα
3. **Αντιστοίχιση Εισηγητικό → Σύμβαση** — τα 208 πεδία με κατάσταση κάλυψης, φιλτραρίσιμα
4. **Μητρώο άρθρων** ανά πρότυπο με ζώνη και συνθήκη ένταξης — η οπτικοποίηση του §5
5. **Πίνακας κάλυψης** (gap dashboard): πόσα πεδία έχουν πηγή, πόσα περιμένουν τη
   Βιβλιοθήκη Όρων, πόσα θέλουν άνθρωπο
6. **Χαρτογράφηση παραρτημάτων** με τα ευρήματα (placeholders, συγκρούσεις)
7. **Προσομοιωτής**: δίνεις τιμές στα πεδία-κλειδιά και βλέπεις ποιο πρότυπο επιλέγεται και
   ποια άρθρα μπαίνουν/βγαίνουν — αυτό μετατρέπει το HTML από τεκμηρίωση σε εργαλείο
   επικύρωσης των κανόνων *πριν* γραφτεί κώδικας

> Για τον ρόλο του HTML ως πρωτοτύπου της τελικής λύσης και για την επεκτασιμότητα σε νέους
> τύπους συμβάσεων, βλ. **§11**.

## 9. Προϋποθέσεις και ανοικτά θέματα

**Blocking — χωρίς αυτά δεν προχωράει:**

1. **Βιβλιοθήκη Προτύπων Όρων.** Ιδιοκτησία: Επιχειρησιακός Χώρος Προμηθειών. Ποιες οι εγκεκριμένες τιμές
   ανά τύπο σύμβασης, ποια η διαδικασία παρέκκλισης. Είναι το 82% της πληροφορίας.
2. **Μοναδικό κλειδί εισηγητικού** και σύνδεσή του με το μητρώο συμβάσεων (Ε-17).
3. **Πρόσβαση σε μητρώο προμηθευτών** για νομική ταυτότητα αναδόχου (επωνυμία, ΑΦΜ, ΓΕΜΗ,
   έδρα, νόμιμοι εκπρόσωποι) — τίποτα από αυτά δεν υπάρχει στο εισηγητικό.

**Αποφάσεις πολιτικής:**

4. **Όριο ποσού** που καθορίζει εγκριτικό όργανο (Ε-16) — δεν προκύπτει από τα δείγματα.
5. **Παράρτημα Παραλαβής**: tokenize ή κλείδωμα των ενσωματωμένων προθεσμιών;
6. **Σιωπηρή αποδοχή**: οι ρήτρες αυτοδίκαιης παραλαβής ισχύουν και για συμβάσεις υπηρεσιών Γ
   ή μόνο για Α/Β;
7. **Τρεις νέες σημαίες ασφάλειας** (κρίσιμη υπηρεσία, δεδομένα καρτών, υψηλή διαθεσιμότητα)
   — ποιος τις συμπληρώνει, πότε;
8. **Πεδία ΤΝ**: `platform.llm_provider`, `llm_switchable`, `session_definition` δεν έχουν
   αντίστοιχο στη σύμβαση. Για λύσεις ΤΝ χρειάζονται νέα άρθρα.

**Τεχνικά:**

9. Legacy `.doc` — τυποποίηση σε `.docx` στην πηγή.
10. Έκδοση & αρχειοθέτηση: κάθε παραγόμενη σύμβαση δεμένη με την έκδοση προτύπου, κανόνων και
    Βιβλιοθήκης Όρων που χρησιμοποιήθηκαν.

## 10. Προτεινόμενη σειρά

| Φάση | Παραδοτέο | Γιατί πρώτα |
|---|---|---|

## 11. Το HTML ως πρωτότυπο της τελικής λύσης

### 11.1 Τι επιβιώνει και τι όχι

Το HTML είναι **οριστικό ως προδιαγραφή, προσωρινό ως αρχιτεκτονική**.

Αυτό που μεταφέρεται αυτούσιο στην τελική λύση δεν είναι η σελίδα — είναι τα **μητρώα σε μορφή
δεδομένων** (JSON): μοντέλο πεδίων, μητρώο άρθρων με ζώνες και συνθήκες, κανόνες, αντιστοίχιση,
βιβλιοθήκη όρων. Αν αυτά ζουν ως δεδομένα, το HTML είναι απλώς **ένας renderer**. Αύριο μπορεί
να είναι .NET service, Power Platform app ή ADO pipeline — ίδια JSON, άλλο περιτύλιγμα.

Αν όμως η λογική γραφτεί *μέσα* στο HTML ως κώδικας, τότε είναι πρωτότυπο μιας χρήσης.
**Αυτή είναι η μία απόφαση που καθορίζει αν η δουλειά θα ξαναγίνει από την αρχή.**

Έχει και άμεση αξία εδώ: όσο οι προδιαγραφές είναι σε εξέλιξη (§0), κάθε αναθεώρηση του
μοντέλου ή των κανόνων γίνεται **αλλαγή δεδομένων** και όχι επανεγγραφή εφαρμογής.

### 11.2 Τι μπορεί όντως να κάνει ο browser

Περισσότερα απ' όσα φαίνεται, και αυτό κάνει το πρωτότυπο αξιόπιστο:

- **Upload & ανάγνωση εισηγητικού** — το `.docx` είναι zip+XML· ο browser έχει native
  `DecompressionStream`, οπότε διαβάζεται χωρίς εξωτερική βιβλιοθήκη
- **Παραγωγή `.docx`** — αντίστοιχα με `CompressionStream`
- **Όλοι οι κανόνες και τα validation checks** — καθαρή λογική, δεν θέλει server
- **Αποθήκευση προτύπων** — ως embedded δεδομένα ή με file-system access

Και ένα πλεονέκτημα που δεν είναι προφανές: **τίποτα δεν φεύγει από το μηχάνημα**. Τα εισηγητικά
φέρουν «Εμπιστευτικό» και τα Μέτρα Ασφάλειας «RESTRICTED USE». Ένα client-side εργαλείο
παρακάμπτει εντελώς τη συζήτηση περί διαβίβασης δεδομένων — για τραπεζικό περιβάλλον, όχι μικρό.

### 11.3 Πού σταματάει

| | Γιατί |
|---|---|
| **Διακυβέρνηση προτύπων** | Τα καθαρά templates θέλουν έλεγχο εκδόσεων σε κεντρικό αποθετήριο |
| **Ιχνηλασιμότητα** | Κάθε σύμβαση δεμένη με εκδόσεις προτύπου/κανόνων/όρων· θέλει μόνιμη αποθήκευση |
| **Διασυνδέσεις** | Μητρώο προμηθευτών, ΓΕΜΗ, μητρώο συμβάσεων, Demand Management — server-side auth |
| **Ταυτόχρονη χρήση** | Πολλοί λειτουργοί, μία βιβλιοθήκη όρων |

Τα τρία πρώτα ταυτίζονται με τα blocking του §9.

### 11.4 Το τεστ της επεκτασιμότητας

Η σωστή ερώτηση δεν είναι «είναι scalable;» αλλά:

> **Μπορεί να μπει νέος τύπος σύμβασης χωρίς να αγγίξει κανείς κώδικα;**

Απαιτεί:

- **Μητρώο προτύπων** — ο τύπος είναι εγγραφή δεδομένων, όχι σταθερά στον κώδικα
- **Modules με `applies_to: [Α, Β, Γ, Δ, …]`** — ο νέος τύπος δηλώνει ποια άρθρα χρησιμοποιεί
- **Κανόνες ως δηλωτικές εκφράσεις** πάνω σε paths πεδίων, όχι `if/else`
- **Namespaced tokens** — `system.*`, `solution.*`, `project.*`, `addendum.*`· νέος τύπος φέρνει
  δικό του namespace χωρίς συγκρούσεις
- **Κοινός πυρήνας + επέκταση ανά τύπο** — ήδη η δομή του μοντέλου

**Σημείο προσοχής:** τα σημερινά `build_templates.py`, `build_module_map.py`, `build_ruleset.py`
έχουν τα Α/Β/Γ/Δ **σκληροκωδικοποιημένα** σε λίστες. Με τη σημερινή μορφή, νέος τύπος =
επέμβαση σε τρία αρχεία κώδικα. Πρέπει να γυρίσει σε δεδομένα πριν μιλήσουμε για επεκτασιμότητα.

Χρήσιμη δοκιμασία: το μοντέλο σηκώνει και **μη-IT** συμβάσεις. Ο κοινός πυρήνας (μέρη, τίμημα,
διάρκεια, GDPR, καταγγελία) μένει· αλλάζει μόνο το φύλλο του τύπου. Αν σχεδιαστεί σωστά, δεν
είναι «σύστημα για IT συμβάσεις» — είναι «σύστημα για συμβάσεις».

### 11.5 Κλιμάκωση

| Επίπεδο | Τι προσθέτει | Πού τρέχει |
|---|---|---|
| 0 | Τεκμηρίωση κανόνων *(σήμερα)* | browser |
| 1 | Προσομοιωτής αποφάσεων | browser |
| 2 | Βιβλιοθήκη προτύπων + μητρώο άρθρων ως δεδομένα | browser |
| 3 | Upload εισηγητικού → εξαγωγή → φόρμα επιβεβαίωσης | browser |
| 4 | Παραγωγή .docx + αναφορά validation | browser |
| 5 | Διασυνδέσεις, audit, διακυβέρνηση | υποδομή |

Τα 1–4 δίνουν **λειτουργικό demo άκρη σε άκρη** χωρίς υποδομή — αρκετό για επικύρωση της
λογικής. Το 5 είναι άλλο έργο, που καταναλώνει τα ίδια JSON.

### 11.6 Τι να μην επιχειρήσει

**Αυτόματη εξαγωγή από ελεύθερης μορφής εισηγητικά χωρίς επιβεβαίωση.** Τα 3 δείγματα είχαν
τρεις διαφορετικές δομές — άλλες επικεφαλίδες, άλλο σύστημα αναγνώρισης, ασύμβατοι πίνακες.
Η ροή πρέπει να είναι **upload → υποψήφιες τιμές με ένδειξη βεβαιότητας → επιβεβαίωση από τον
λειτουργό**. Ποτέ σιωπηλή εξαγωγή σε νομικό έγγραφο.
